# Routine guardrails

Scoped routine definitions inherit the compiled hard floor and versioned installation recommendations. Project definitions also inherit tenant and project rules; personal definitions inherit tenant and owner-user rules; workspace definitions inherit tenant rules. Legacy ticket-only recurrences keep their existing behaviour. Saving policy grants no launch consent, and automatic execution remains off.

`GET /api/recurrences/{recurrenceId}/guardrails` reads the applicable policy and digest. A person session can replace a scoped rule revision with `PUT` on that route, supplying `scope`, `expected_revision`, `rules` and an optional `reason`. Tenant and project edits require their current administrator. User edits require the canonical owner. Removing a restriction, changing its predicate or reducing its outcome requires a current administrator and a reason. Append-only revisions retain the person, prior revision, inherited digest and exact replacement digest. Changed inherited evidence fails closed until the exception is explicitly revised.

Save and action checkpoints run the same deterministic engine. Block takes precedence over needs-person and allow. Rules use bounded word, path, size or registered compiled-template predicates; they never run arbitrary shell. Hard policy and template hashes cannot be replaced by a routine, agent or administrator. Protected artifact changes include both sides of renames and copies. The workspace broker must supply resolved paths and enforce symlink and worktree confinement.

Each persisted evaluation binds the definition revision, context and effective policy digests, hard and preset versions, and every applicable rule's result and reason. Action decisions always require verified different-family evaluation before execution; this slice records that requirement but does not launch an evaluator or provide an execution grant. The later action broker and evaluator consume this boundary within their final authorized write transaction.
