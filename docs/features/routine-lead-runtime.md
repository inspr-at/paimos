# Qualified routine lead runtime

Routine dispatch records demand for an explicitly requested project lead. The
paired daemon polls only owner-approved project mappings. A live or adopted
lead is retained; queue membership does not request Start lead or authorize a
replacement. Projects remain off by default, with a visible reason when consent,
qualification, native mapping, admission facts or executor wiring is missing.

The additive `lead-runtime` API offers project polling, an exact-generation claim
and process reports. Claim fences tenant, tree and pairing, repeats owner and
routine consent, and requires a role-resolved native account and a distinct held
lead attempt in the existing routine budget. It registers an owned root session,
records one generation and persists the claim before any process launch. Lost
claim replies replay the same claim. A changed daemon, proof, checkout or intent
cannot borrow that authority.

The daemon keeps a private versioned receipt beside its existing journal. Its
shared pairing ledger counts the root lead in the existing dial. Workers poll
first. Native execution requires an independently qualified lead adapter and the
existing worktree/resource allocation seam. The receipt is marked attempted
before calling the adapter. An uncertain start or old daemon generation freezes
recovery; a persisted PID never authorizes adoption, signalling or relaunch.

Preflight repeats the deterministic live start gates. The executor must bind the
grant expiry to the current window boundary, resolve the owner's lead model
through the registry, reserve its account and run-wide allowance, and retain
unknown costs or fixture ownership. A reserved process may complete after the
window closes. Started and exit reports identify the same native process; chat
turn completion and heartbeat expiry do not release its slot. Resource and
ledger release also require the native adapter's confirmed exit and fixture
exit proof. The executor owns dispatch and continuation through the existing
routine loop; no external worker-run script or recursive evaluator is used.

Live receipts publish the same owned session's heartbeat. The separately
qualified native adapter services cooperative pause, controls and leased inbox
delivery through callbacks bound to that session, without receiving a daemon
API key. Qualification must prove durable delivery/control replay and exact
process/deadline checks. A ledger rebuild refuses unknown lead receipts rather
than reconstructing occupancy from worker journal rows alone.

`routineexec.Options.LeadRuntime` supplies the transaction-only actor preparation,
validation and reconciliation callbacks; `agentd.Config.LeadRuntime` supplies
owner-approved local mappings and allocation. These are qualification seams,
not enable settings. Production intentionally installs no qualified automatic
lead reserver, local mapping or native lead adapter until coordinator/OPS
qualification and the separate person-owned project flip. Unsupported routes
remain visibly unavailable. This slice performs no native model calls and adds
no migration or release coordinate.
